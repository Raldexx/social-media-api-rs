# Social Media API

A social media backend written in **Rust** with the [RustAPI](https://github.com/Tuntii/RustAPI) framework, **PostgreSQL** and **JWT** authentication.

This project is a Rust rewrite of my FastAPI project, [social-media-api](https://github.com/Raldexx/social-media-api). It keeps every feature of the original and adds **posts, likes and follows**. Roles are now attached to users and their permissions are actually enforced.

Interactive API documentation (Swagger UI) is generated automatically and served at `/docs`.

---

## Features

- **Authentication**: register, login, refresh and logout with short-lived access tokens and long-lived refresh tokens
- **Users**: profile, update, change password, deactivate account, public profiles, search, follower / following / post counters
- **Posts**: create, read, list (paginated), delete
- **Likes**: like and unlike a post
- **Follows**: follow and unfollow, followers and following lists (paginated)
- **Roles and permissions**: every user has a role. The role decides who can post, like and delete, how many posts a day are allowed, and how many followers a user may have
- **Admin tools**: create, update and delete roles, assign roles to users
- **Production basics**: CORS, request IDs, structured logging, health endpoints, graceful shutdown, automatic database migrations

## Built with RustAPI

RustAPI is a FastAPI-style framework for Rust. In this project it provides:

- **Attribute routing**: a handler is registered with one line, for example `#[rustapi_rs::get("/api/v1/posts")]`. All 30 endpoints register themselves this way.
- **Automatic OpenAPI and Swagger UI** built from those handlers and their types.
- **Typed extractors** such as `Json`, `Path`, `Query` and `State`, so request data arrives already parsed.
- **A consistent error type** (`ApiError`) for 400, 401, 403, 404, 409 and 500 responses.
- **Production defaults**: request IDs, tracing, `/health`, `/live` and `/ready`.
- **Pluggable extractors**: authentication is a small custom extractor (`AuthClaims`) that plugs into the framework, so a protected endpoint only has to list it as an argument.

The business logic (SQL, roles, permissions, validation, password and token handling) does not depend on the framework, so the web layer could be swapped without rewriting it.

## Getting started

### Requirements

- **Rust 1.88 or newer.** RustAPI states 1.85, but one of its dependencies (`time`) needs 1.88.
- **PostgreSQL 14 or newer** (developed and tested on 16).
- Python 3 is only needed for the optional test script.

### 1. Start a database

Use any PostgreSQL you already have, or run one with Docker:

```bash
docker run --name sma-db \
  -e POSTGRES_USER=sma -e POSTGRES_PASSWORD=sma -e POSTGRES_DB=sma \
  -p 5432:5432 -d postgres:16
```

### 2. Configure

```bash
git clone https://github.com/Raldexx/social-media-api-rust.git
cd social-media-api-rust
cp .env.example .env      # Windows: copy .env.example .env
```

Open `.env` and set `SECRET_KEY` to a long random string.

### 3. Run

```bash
cargo run
```

The tables are created automatically on start-up (see `migrations/`). The first build takes a few minutes because dependencies are compiled.

Open **http://127.0.0.1:8000/docs** to explore and try every endpoint.

### 4. Create the first admin

There is intentionally no public endpoint for this. Register a normal account, then run this once in `psql`:

```sql
UPDATE users SET is_superuser = TRUE WHERE email = 'you@example.com';
```

### Quick try with curl

```bash
# Register (the response contains access_token and refresh_token)
curl -X POST http://127.0.0.1:8000/api/v1/auth/register \
  -H "Content-Type: application/json" \
  -d '{"username":"alice","email":"alice@example.com","password":"Passw0rdOK","full_name":"Alice"}'

# Create a post
curl -X POST http://127.0.0.1:8000/api/v1/posts \
  -H "Authorization: Bearer <ACCESS_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"content":"Hello from Rust!"}'

# Read the latest posts (public)
curl "http://127.0.0.1:8000/api/v1/posts?limit=10"
```

On Windows PowerShell the quoting is different. The Swagger UI at `/docs` is the easiest way to try things there.

## API overview

All endpoints live under `/api/v1`. Protected endpoints need the header `Authorization: Bearer <access_token>`.

| Area | Endpoint | Auth | Notes |
|------|----------|------|-------|
| **Auth** | `POST /auth/register` | no | Returns user and both tokens |
| | `POST /auth/login` | no | |
| | `POST /auth/refresh` | no | Send a refresh token, get a new access token |
| | `POST /auth/logout` | no | Tokens live on the client, so the client deletes them |
| **Me** | `GET /users/me` | yes | Full profile including email and role |
| | `PUT /users/me` | yes | Updates only the fields you send |
| | `DELETE /users/me` | yes | Deactivates the account (soft delete) |
| | `PUT /users/me/password` | yes | Requires the old password |
| | `GET /users/me/stats` | yes | Follower, following and post counts |
| **Users** | `GET /users/search?q=` | no | Case-insensitive, active users only |
| | `GET /users/{username}` | no | Public profile (no email) |
| | `GET /users/{id}/stats` | no | Counters by numeric id |
| | `PUT /users/{username}/role` | admin | Body: `{"role_id": 2}` |
| **Roles** | `GET /roles`, `GET /roles/{id}` | no | |
| | `POST /roles` | admin | |
| | `PUT /roles/{id}` | admin | Updates only the fields you send |
| | `DELETE /roles/{id}` | admin | Blocked while users still have the role |
| **Posts** | `POST /posts` | yes | Needs `can_post`, respects `max_posts_per_day` |
| | `GET /posts` | no | Newest first, `?limit=&offset=` |
| | `GET /posts/{id}` | no | |
| | `GET /users/{username}/posts` | no | `?limit=&offset=` |
| | `DELETE /posts/{id}` | yes | Own post: `can_delete_own_posts`. Someone else's: `can_delete_any_posts` |
| **Likes** | `POST /posts/{id}/like` | yes | Needs `can_like`. Returns the updated post |
| | `DELETE /posts/{id}/like` | yes | |
| **Follows** | `POST /users/{username}/follow` | yes | The followed user's `max_followers` is enforced |
| | `DELETE /users/{username}/follow` | yes | |
| | `GET /users/{username}/followers` | no | `?limit=&offset=` |
| | `GET /users/{username}/following` | no | `?limit=&offset=` |
| **Info** | `GET /`, `GET /health`, `GET /live`, `GET /ready` | no | |

Input rules: usernames are 3 to 50 characters (letters, digits, underscore) and stored in lowercase. Passwords are 8 to 100 characters with an uppercase letter, a lowercase letter and a digit. Posts are 1 to 1000 characters.

## Authentication

- Passwords are hashed with **Argon2id**. Hashing runs on a blocking thread so it never stalls the async server.
- Login returns an **access token** (30 minutes by default) and a **refresh token** (7 days by default).
- Every token carries a `typ` claim (`access` or `refresh`). A refresh token is rejected as an access token and the other way around.
- On every protected request the user is loaded from the database. Deleted users get `401` and deactivated users get `403`, even if their token has not expired yet.

## Roles and permissions

Each user has exactly one role. New users get the default `user` role, which cannot be deleted. Admins (`is_superuser`) skip role checks.

| Role setting | What it controls |
|--------------|------------------|
| `can_post` | Creating posts |
| `max_posts_per_day` | Posts allowed in a rolling 24 hours |
| `can_like` | Liking posts |
| `can_delete_own_posts` | Deleting your own posts |
| `can_delete_any_posts` | Deleting other people's posts (moderators) |
| `max_followers` | Followers a user with this role can have |
| `is_active` | An inactive role grants nothing |
| `can_comment`, `can_ban_users`, `can_verify_users`, `can_manage_roles` | Stored for future features, not used yet |

## Data model

| Table | Purpose |
|-------|---------|
| `roles` | Permissions and limits |
| `users` | Accounts. Each row points to one role and keeps follower, following and post counters |
| `posts` | Posts, with a like counter |
| `likes` | One row per (user, post) |
| `follows` | One row per (follower, followed user) |

The schema lives in [`migrations/0001_init.sql`](migrations/0001_init.sql) and is applied automatically when the server starts.

## Design notes

- **Counters stay correct under load.** Like, follow and post counters are updated in the same transaction as the row they describe, and a test checks them against the real rows after concurrent requests.
- **Daily post limit cannot be bypassed by parallel requests.** The user's row is locked while the limit is checked, so ten simultaneous posts with a limit of one result in exactly one success.
- **No deadlocks on mutual follows.** Both counters are updated in a single statement.
- **No ORM.** Queries are plain SQL, checked by the end-to-end tests.
- **Deactivation is a soft delete.** The data stays, and the account disappears from search, lists and follow actions.

## Testing

`smoke_test.py` talks to a running server over HTTP and needs only the Python standard library.

```bash
# Start the server first (cargo run), then:
python smoke_test.py
```

This runs 89 checks covering registration, login, tokens, profiles, search, posts, likes and follows. To also test roles and permissions, pass an admin account (see "Create the first admin"):

```bash
python smoke_test.py --admin-email you@example.com --admin-password 'YourPassword1'
```

That runs all 121 checks, including that roles really change what users can do.

## Differences from the FastAPI version

- Password hashing moved from bcrypt to **Argon2**. Old hashes are not compatible, so start with a fresh database.
- Refresh tokens can no longer be used as access tokens.
- Roles are linked to users and enforced.
- The username and password rules from the original `UserCreate` schema are now applied.
- `/roles/` is now `/roles` (no trailing slash).
- Error bodies use RustAPI's format instead of FastAPI's `{"detail": ...}`.
- Search treats `%` and `_` as normal characters.
